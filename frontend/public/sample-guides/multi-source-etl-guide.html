1Define the problem

The same discipline as any onboarding: write down what's broken across the eight silos and what a single, governed ingestion platform needs to guarantee before a single pipeline gets built.

Business & technical context

The enterprise runs its business across eight disconnected systems, each integrated ad hoc by a different team, at a different time, with a different scripting language: SAP S/4HANA (finance & supply chain), Salesforce (CRM), Workday (HR), Oracle E-Business Suite (legacy finance, being sunset over 18 months), an on-prem SQL Server order-management system, a vendor invoice drop over SFTP, a marketing REST API (ad spend), and a website clickstream event feed. Finance, sales ops, and the executive dashboard each need a consolidated view none of these systems can give alone.

Pain points today 8 different integration scripts (Python cron jobs, a Talend flow, two manual Excel exports) with no shared logging, no shared naming, no shared metadata — an analyst joining SAP GL data to Salesforce opportunity data has to reverse-engineer two completely different lineage models. Each new source integration takes 4–6 weeks of bespoke engineering.
Scaling & governance exposure No consistent secret handling — two of the eight scripts have credentials in a config file checked into a private repo. No standard cadence policy, so some feeds are "whenever someone remembers to run the script." Onboarding a 9th source today means onboarding a 9th bespoke pattern, not reusing the other eight.

Goals & success criteria

  • One ingestion pattern, eight source types — relational tables (SAP, Oracle EBS, SQL Server), SaaS REST APIs (Salesforce, Workday, marketing), SFTP flat files, and a streaming event feed all land through the same governed pipeline family, not eight bespoke ones.
  • Full + incremental parity everywhere — every object supports an initial full seed and an ongoing incremental load appropriate to its API/connector's change-capture capability.
  • Cadence matched to source reality, not a blanket policy — SAP/Oracle/SQL Server finance data on a daily close cadence, CRM/HR/marketing on hourly sync, clickstream near-real-time.
  • One metadata and logging contract across all eight sources — an analyst should not be able to tell, from the curated layer, which of the eight systems a row originated from without reading _source_system.
  • New source onboarding measured in days, not weeks — the 9th, 10th, 11th source should reuse the same wizard, the same folder convention, the same control table.
  • Nothing reaches production without validation and review — same governed Git → PR → CI/CD path for every one of the eight sources, no exceptions for "it's just a small feed."

2Approach

A medallion lake fed by a small number of generic, metadata-driven pipelines — one orchestrator per source system reading a shared control table — rather than one pipeline per object multiplied by eight sources. Every artifact is authored through ADF Forge's Build form so eight very different connector types produce structurally identical, governed output.

High-volume load: chunking & parallel extraction

The SAP FI/CO historical seed (12 years of GL line items, ~640M rows via the ODP extractor) and the Oracle EBS GL backfill feeding the same curated table are the two objects too large for a single Copy activity — and SAP's RFC/ODP session is also the most expensive resource here to hold open, so chunking has to protect the source as much as speed up the load.

1Chunk-plan control tableSAP: one chunk per fiscal period (12 years × 12 periods = 144 chunks). Oracle EBS: one chunk per calendar quarter.
→
2Lookup + ForEachSAP orchestrator: batchCount = 3 (protects the RFC/ODP gateway). Oracle EBS: batchCount = 6 (DB connector, more headroom).
→
3Copy per chunkSAP: ODP delta-queue package extract per period. Oracle EBS: dynamic range partition on last_update_date, parallel copies 8.
→
4Merge to curatedEach chunk upserts into curated.gl_transaction keyed on (_source_system, natural key) — safe to run out of order
  • Chunk size follows the source's natural grain, not a fixed row count: SAP chunks by fiscal period because that's how the ODP extractor's delta queue is structured; Oracle EBS chunks by date range because last_update_date is its only reliable partition column. A one-size-fits-all row-count chunk plan doesn't hold across eight different connector types.
  • Per-source parallelism reflects per-source cost: SAP's batchCount = 3 is intentionally the most conservative of the eight orchestrators — an RFC/ODP session left open too long, or too many held in parallel, is the single most common way this kind of integration gets throttled or blocked by the SAP Basis team.
  • Restartable per chunk, cross-source safe: the shared chunk-control table's status column (PENDING/RUNNING/SUCCEEDED/FAILED) is scoped per source_system, so a failed SAP period-37 chunk retries independently of Oracle EBS's own chunk plan even though both write into the same curated table.
  • Merge keyed to survive out-of-order and cross-source writes: because SAP and Oracle EBS both upsert into curated.gl_transaction, the merge key includes _source_system — two chunks from different sources (or out-of-order periods from the same source) can never collide or overwrite each other's rows.
!
Why SAP gets the smallest batchCount of any of the eight sources

Every other source here is either a cloud API with its own scaling (Salesforce, Workday, the marketing API) or a database ADF can query as hard as its own connection pool allows (Oracle EBS, SQL Server). SAP is the one system a badly-tuned chunk plan can visibly disrupt for other consumers, so its concurrency ceiling comes from the SAP Basis team's guidance, not from ADF Forge's defaults.

Target table & file naming standardization

Eight sources funneling into shared curated tables — SAP and Oracle EBS both write curated.gl_transaction — makes an ad hoc target name per source untenable; the same object would end up with two different destinations depending on who built the pipeline. One fixed pattern per target kind, built from the same {source}/{object} tokens as the pipeline naming pattern removes the choice entirely:

Target kindPatternExample
Curated entity table (shared across sources)curated.<entity:snake>curated.gl_transaction, curated.crm_account
Warehouse mart tablemart.<domain:lower>_<entity:snake>mart.finance_gl_fact, mart.sales_pipeline_fact
Partner-facing file extract<entity>_<source:lower>_<yyyyMMdd>.csvgl_transaction_sap_20260912.csv
Vendor-invoice archive filevendor_invoice/ingest_date=YYYY-MM-DD/<vendor>_invoice_<yyyyMMdd>.csvvendor_invoice/ingest_date=2026-09-12/acme_invoice_20260912.csv

Because curated.gl_transaction is a fan-in target for two different orchestrators, the pattern is set once at the entity level, not per source — the Onboarding row for both the SAP and Oracle EBS GL objects points at the same target-name field (§26.2), so a change to the pattern (a schema rename, say) only has to happen in one place and both orchestrators pick it up. The same warn/block enforcement that catches a malformed pipeline name catches a target name that skips the curated./mart. zone prefix or reuses another entity's table — before a PR is opened, not after a ninth source shows up expecting the convention to already be obvious.

Bronze/Silver/Gold layer-specific pipelines

The target architecture above names three zones — Landing/Raw, the Bronze/Silver curated zone, and Gold marts. Build's first step (Basics → Layer) makes that a real, per-pipeline choice instead of an architecture diagram nobody enforces: pick Bronze, Silver, or Gold and Build generates that layer's pipeline shape.

Bronze — raw ingestion Exactly the eight orchestrators already described above: a plain metadata-driven copy from each source into raw.<source>_<object>. No transformations — this is today's pipeline shape, unchanged.
Silver — conformed/curated Reads the landed Bronze object and appends a transformation chain — conform column names, dedupe on a natural key, cast types, or maintain SCD2 history — before writing the shared curated.<entity> table (e.g. curated.gl_transaction, fed by both the SAP and Oracle EBS orchestrators).
Gold — business marts Joins curated entities and aggregates them into a business-facing mart.<domain>_<entity> table — e.g. mart.finance_gl_fact, joining curated.gl_transaction with curated.customer and aggregating by customer and posting month.

The target table name is computed from the entity/domain you enter, not freely typed — the same "no ad hoc target name per source" discipline as the naming standard above, now enforced by construction for every layer, not just documented in this guide.

!
What "reads the landed Bronze object" means today

Each layer's pipeline is generated independently — a Silver pipeline re-copies from the original source rather than literally chaining off a separate Bronze pipeline's own run. The planned STTM registry below (source_object_keys) formalizes the *intended* lineage (which Bronze/Silver objects a Silver/Gold entity is built from) as persisted metadata, which is a step toward real Bronze→Silver→Gold chaining, but doesn't by itself change how a generated pipeline executes.

Bulk-onboarding Silver/Gold with an STTM workbook (target design)

Typing a curated entity name and hand-building a transformation chain works for one pipeline at a time, but the inventory above has eight sources landing into a handful of shared curated entities (curated.gl_transaction, curated.customer, …) and several marts built on top of them — that's naturally a bulk-authoring problem, not a one-row-at-a-time one. The STTM registry (target design, not built yet) plans a downloadable, multi-tab STTM (Source-to-Target Mapping) Excel workbook for exactly this: one sheet per curated entity or mart, a worked example sheet, and a reference sheet listing every transformation and data-quality rule type the tool supports.

1. Download the template From Onboarding's Silver or Gold tab — a separate workbook per layer, since their mandatory columns and transformation vocabularies differ.
2. Fill one sheet per entity E.g. a curated_gl_transaction sheet listing its source_object_keys (the SAP and Oracle EBS Bronze objects it's built from), a mandatory classification tag, and up to 10 transformation rows (conform columns, dedupe, cast, or — per the widened rule set — a join) plus up to 5 data-quality rows.
3. Upload, preview, commit Each sheet is validated independently; valid sheets commit into the Silver/Gold registry, ready to pick from a dropdown in Build's Basics step instead of retyping any of this per pipeline.

A mart like mart.finance_gl_fact — joining curated.gl_transaction with curated.customer — is exactly the case that motivated widening the transformation rule set: Gold objects can now use scd2 (for a slowly-changing customer dimension feeding the fact table) alongside join/aggregate, and a Silver entity built from two sources can use join during conformance, not only after landing in Gold.

Data quality checks

Two sources (SAP and Oracle EBS) write into the same curated.gl_transaction table — exactly the shared-target case where a bad row from either side is hardest to trace back. Each rule below is authored on the object in Build's Pipeline Settings step (up to 5 per pipeline) and becomes a real pre-copy Lookup activity in that object's generated child pipeline, independent of which source it came from:

ObjectRuleConfigEnforcementGenerated as
GL_TRANSACTION (SAP & Oracle EBS)IS_NOT_NULLcolumn TransactionIdBlockDQ_transaction_id_required_Check (Lookup) → DQ_transaction_id_required_Gate (IfCondition → Fail)
GL_TRANSACTIONRANGE_BETWEENcolumn Amount, value -1000000,1000000WarnLookup only — flags an out-of-range posting for finance to review without stopping either source's daily close
CUSTOMER (Salesforce)REGEX_MATCHcolumn Email, value %@%WarnLookup only, using T-SQL PATINDEX as the built-in approximation — swap in a real regex/CLR check if your target engine supports one

This app never runs the check itself or reads either system's live data (§30.3's scope boundary) — the Lookup's SQL executes in ADF, at run time, like any other generated activity. Because Block is itself a Standards enforcement level (§25.2), a shared-table scenario like this can require "primary key not-null, blocking" as an org policy rule regardless of which of the 8 sources authors the pipeline.

!
File-arrival cadence for the SFTP vendor feed

The vendor invoice drop doesn't run on a clock — it fires from a storage-event trigger the moment the file lands (typically between 01:00–04:00 UTC, vendor-dependent), then falls back to a 06:00 UTC schedule trigger as a safety net so a missed event doesn't silently skip a day.

Orchestration design

Eight metadata-driven orchestrators run independently — one per source, on its own schedule — but two of them, SAP and Oracle EBS, write into the same curated table, so orchestration also has to manage a dependency between sources, not just within one.

Per sourcepl_hub_<source>_orchestratorLookup control table for objects due → ForEach (batchCount tuned per source) → Execute Pipeline per object
→
GuardSAP → Oracle EBS sequencingOracle EBS's tumbling window declares a trigger dependency on SAP's daily run — EBS never starts until SAP's GL merge for that day has succeeded
→
AggregateIf Condition, per orchestratorAny child object failure fails that source's run as one alert, filtered by source_system in the shared log
→
DownstreamCross-source mart refreshTriggered only once all same-day-cadence orchestrators report success — not on a fixed clock offset
Within a source: fan-out with a concurrency ceiling Each of the eight orchestrators is the same shape — Lookup the control table's due objects, ForEach with a per-source batchCount, Execute Pipeline per object with wait-on-completion — but the ceiling itself is tuned per source (SAP 3, Salesforce 4 to respect Bulk API limits, the rest 6–8).
Across sources: an explicit dependency, not a time gap Rather than scheduling Oracle EBS "30 minutes after SAP and hoping," EBS's trigger declares a real dependency on SAP's run succeeding — the same tumbling-window-dependency mechanism used for the hourly sources' self-dependency, applied across pipelines instead of within one.
  • Independent pattern for the one non-batch source: the clickstream pipeline is deliberately outside every orchestrator — it has its own tumbling-window self-dependency so a slow 2-minute window can't overlap the next one, and no other source's failure can ever block or delay it.
  • Restartable per object, not per source: a re-run of the Salesforce orchestrator after a partial failure only re-executes the child pipelines whose control-table row didn't reach SUCCEEDED — the other objects (and the other seven sources) are untouched.
  • One shared failure surface: whether the failure is a chunked SAP backfill, a per-object child pipeline, or the clickstream feed, every run writes to the same execution log filtered by source_system — eight orchestrators, one on-call dashboard.
  • Scales to a 9th source without new orchestration engineering: a new source gets its own orchestrator built from the same Build template; it only needs an explicit trigger dependency added if it shares a curated table with an existing source, same as the SAP → Oracle EBS case above.

Built with ADF Forge — step by step

  1. Connections: Create the ten linked services from the matrix above, each tagged Source (lake/warehouse tagged Target); every credential/API key/connection string is a Key Vault reference.
  2. Onboarding: One CSV import per source (8 imports covering ~65 objects) — Upload → Map columns → Validate → Commit; the SAP and Oracle EBS rows are flagged during Validate for pointing at the same target table, confirmed as intentional (the EBS-sunset design).
  3. Build → Basics, per source: Generation template = Metadata-Driven Load for the seven table/API/file sources; pipeline pattern = independent for the Event Hub clickstream pipeline (it isn't object-list-driven). Layer = Bronze for each source's raw ingestion orchestrator; the curated gl_transaction/crm_account/etc. entities and the finance/sales marts are each their own Silver/Gold pipeline (see Bronze/Silver/Gold layer-specific pipelines).
  4. Build → Source/Target, per source: Pick that source's saved connection; source objects prefill from Onboarding; watermark column(s) set per the change-capture column in the matrix.
  5. Build → Pipeline Settings, per source: Retry/backoff tuned per source's API rate limits (e.g. Salesforce Bulk API retry with exponential backoff); the 11 standard metadata columns and Azure Monitor logging attached identically across all eight. SAP's and Oracle EBS's one-time historical seeds additionally set Partition & chunking (144 fiscal-period chunks / batchCount 3 for SAP, quarterly chunks / batchCount 6 for EBS — see High-volume load above).
  6. Review & Generate, per source: Eight separate Generate actions produce eight orchestrator pipelines (plus their datasets, linked services, triggers) as new DRAFTs — never one giant pipeline for all sources.
  7. Validate: Standards' connector allow-list, required tags, and Key-Vault-only rule run against all eight source's artifacts identically.
  8. Push to Git → PR, per source: Eight feature branches, eight PRs into dev — reviewed independently by each source's owning team, merged on their own schedule, but landing in the one shared repository the CI/CD pipeline below watches.

Per-source blast radius, shared pipeline

Because the ARM deploy is incremental and the smoke test filters by source_system, eight teams share one CI/CD configuration without one source's bad deploy blocking or masking another's — the exact scaling property a one-pipeline-per-source approach couldn't offer without eight times the CI/CD engineering.

Promoting onboarded source & control-table metadata

The factory-wide ARM template in stage 2 only carries the ADF artifacts — pipelines, datasets, linked services, triggers — for all eight sources together. It says nothing about which of the ~65 onboarded objects are enabled, their watermark column, or their target path — that shared inventory lives in control.adf_control_table, the single table every one of the eight metadata-driven orchestrators Lookups at runtime. Promoting it across Dev → Test → Prod rides the same PR and the same shared CI/CD run as the ARM deploy above, per source:

  1. Onboard or update a source's rows in ADF Forge: that source's team runs its own Onboarding CSV import or manual-grid edit, then Generate control-table SQL produces <sql>/adf_control_table.sql (DDL plus one seed INSERT per enabled object, scoped to that source's rows) and an objects.csv snapshot — committed to that source's own feature branch and PR, never hand-typed against a live database.
  2. Reviewed alongside that source's pipeline diff (stage 1): the owning team's reviewer sees only its own control-table row changes — e.g. a new SAP fiscal-period object or an edited Salesforce watermark column — not the other seven sources' rows, even though every source shares the one table.
  3. Applied to Dev's control database (parallel to stage 3): a CI/CD step runs that source's adf_control_table.sql against the Dev control-table database — connection resolved from Project Settings → Metadata & parameters, credential from Key Vault, never typed into ADF Forge or the script — as an idempotent upsert, so the other seven sources' rows are untouched.
  4. Proven by the per-source smoke test (stage 4): that source's orchestrator run succeeding confirms the ARM-deployed pipeline and the newly promoted control-table rows agree for its objects specifically, without needing to re-run all eight sources' smoke tests.
  5. Promoted unchanged to Test, then Prod (stages 5–6): the identical per-source adf_control_table.sql artifact — never hand-edited or regenerated per environment — is applied to Test's and Prod's own control databases under that source's own QA and change-advisory sign-offs, so a 9th source added later, or one source's cutover, never touches the other seven sources' already-promoted rows.
  6. Rollback: every source's adf_control_table.sql is retained and versioned by the CI/CD run number, exactly like the ARM template — a bad promotion for one source (an object enabled too early, a wrong watermark seed) is fixed by re-applying that source's previous run's SQL artifact, never by hand-editing rows in the shared live control table.

Governance & scaling notes

  • Connector allow-list: Standards' Connection category restricts new pipelines to the ten approved connector/linked-service types above at Block — a team can't quietly wire up an eleventh ad hoc integration outside this pattern.
  • Onboarding a 9th source: register its connector in Connections (reusing the registry if the connector type already exists, e.g. a second REST API source), import its object list in Onboarding, generate one Metadata-Driven orchestrator in Build — no changes needed to the shared CI/CD pipeline, the metadata contract, or the execution log schema.
  • EBS sunset path: when Oracle EBS retires, its orchestrator pipeline and linked service are simply disabled and later removed via a normal PR — the shared curated.gl_transaction table and every downstream mart query are unaffected, since _source_system already isolates EBS's rows.
  • Cost/ops note: the near-real-time clickstream pipeline is the only one billed on a continuous tumbling-window cadence — it's scoped to the one feed with an actual sub-hour business need, not applied as a default across all eight sources.
