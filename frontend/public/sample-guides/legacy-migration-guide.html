1Define the problem

Before any pipeline gets built, the reference project starts by writing down exactly what is broken today and what "done" looks like — the same discipline any real onboarding should apply before opening ADF Forge's Build wizard.

Business & technical context

Legacy Policy Administration System (PAS) is an on-premises SQL Server 2008 R2 instance that has run the insurer's policy, endorsement and claims-intake data since 2005. It is the system of record for 40+ tables and also drops three nightly flat-file exports (agent commission statements) onto a Windows file share for a downstream finance job. It must be decommissioned within 12 months as part of the platform's cloud migration, but every downstream report, the actuarial data mart, and two partner data-sharing feeds depend on its data.

Pain points today One monolithic nightly batch job (4+ hours) with no restart/checkpoint; every load is a full truncate-and-reload, even for a 200M-row claims table; no incremental capability; no per-run audit trail; connection strings and credentials hardcoded in SSIS packages; no naming or folder convention — new packages are copy-pasted and drift over time.
Compliance & risk exposure No column-level lineage from source to mart, which fails the insurer's most recent SOX data-lineage audit finding. No row-level change history (regulator requires 7-year policy history, not just current state). No structured error/rejection log — failures are found by downstream teams noticing missing rows, days later.

Goals & success criteria

  • Parity load types — every table supports both a Full Load (initial seed / re-seed) and an Incremental/Delta load (ongoing), chosen per table by volume and change rate, not a one-size-fits-all job.
  • Cadence that matches the business need — most reference/dimension tables move daily; high-churn claims tables move hourly; the claims-intake event feed that underwrites same-day fraud scoring moves near-real-time.
  • One metadata contract — every landed row carries the same audit/lineage columns regardless of source table, satisfying the lineage audit finding without a bespoke solution per table.
  • Standard, structured logging — a single execution log the platform team can alert on, instead of tribal knowledge about which job silently failed.
  • A governed path to production — nothing reaches the customer's ADF factory without validation, peer review (PR) and a controlled, auditable deployment — never a hand-run script against prod.
  • Faster to build than the legacy job was to maintain — onboarding a new PAS table should be an hour of configuration, not a new hand-written SSIS package.

2Approach

Land everything into a governed medallion lake first, curate into the reporting warehouse second, and never write pipeline code by hand — author every artifact through ADF Forge's metadata-driven Build form so the generated ADF JSON is consistent and pre-validated by construction.

Where ADF Forge fits

⚙
ADF Forge is the authoring and governance layer, not the runtime

ADF (the customer's own Data Factory) is what actually executes copy activities and data flows against PAS and the lake/warehouse. ADF Forge is the control plane the migration team uses to design, validate, and ship those pipelines as Git-tracked artifacts — it never runs a pipeline or reaches into PAS itself.

  1. Onboarding. The 40+ PAS tables and 3 export files are registered once in Delivery → Onboarding, via a single CSV import (object name, target table, file format, load behaviour, watermark column) rather than 43 separate conversations. This becomes the control-table seed and pre-fills Build's source-object list.
  2. Connections. Two linked services are saved once in Delivery → Connections: PAS-SQLServer-OnPrem (SQL Server connector, self-hosted integration runtime, Windows auth via a Key Vault secret reference) and PAS-FileShare-SFTP for the three exports — plus the ADLS Gen2 and Synapse targets. Every pipeline below picks these from a list instead of re-typing connection details.
  3. Build. Each table's pipeline is authored in Delivery → Build → Pipeline: the 5-step wizard (Basics → Source → Target → Pipeline Settings → Review & Generate) picks the generation template — Full Load for the 9 small reference tables, Incremental/Delta (watermark) for the 24 transactional tables, Composite Watermark for the 3 tables with multi-column change tracking, and a single Metadata-Driven pipeline for the remaining long-tail objects — so one generic pipeline, not 40 bespoke ones, drives most of the load.
  4. Standards. Naming (pl_pas_<object>_<load>), required tags (data-domain, pii, source-system), and the always-on "secrets as Key Vault reference only" rule are enforced at Block before anything reaches Validate — closing the exact hardcoded-credential problem the legacy SSIS packages had.
  5. Validate → Push to Git → PR. Generated artifacts are checked against ADF schema and the Standards policy, then pushed to a feature branch (feature/pas-migration-<object>) and opened as a pull request into dev. ADF Forge never pushes to dev directly, and never deploys anywhere — the PR merge is the handoff into the CI/CD pipeline described below.

High-volume load: chunking & parallel extraction

The 210M-row dbo.ClaimsIntake table is too large to move as a single Copy activity for its historical seed — one long-running query against PAS risks lock contention with the 40 other tables sharing that SQL Server, a multi-hour activity with no restart point, and a 210M-row merge into curated as one all-or-nothing transaction. The Initial Load template's chunking option splits the one-time historical backfill into bounded, independently restartable pieces instead.

1Chunk-plan control tableA one-time stored proc divides the row range into ~21 chunks of ~10M rows on claim_id
→
2Lookup + ForEachOrchestrator reads the chunk plan; ForEach runs with batchCount = 5, not sequential
→
3Copy per chunkDynamic range partition on claim_id, parallel copies 8, writes to its own raw-zone chunk file
→
4Merge to curatedOne idempotent upsert (merge on claim_id) once every chunk reports SUCCEEDED
ChunkRange (claim_id)Est. rowsStatus
chunk_011 – 10,000,000~9.8MSUCCEEDED
chunk_0210,000,001 – 20,000,000~10.1MSUCCEEDED
…………
chunk_14130,000,001 – 140,000,000~9.9MFAILED — retrying
chunk_21200,000,001 – 210,400,000~10.4MPENDING
  • Restartable by chunk, not by table: the chunk-control table tracks per-chunk status; a re-run of the orchestrator skips every chunk already SUCCEEDED and retries only FAILED/PENDING ones — chunk_14 failing on a transient IR timeout doesn't cost re-copying the other 20 chunks.
  • Bounded parallelism, not maximum parallelism: batchCount = 5 caps how many chunks run concurrently against PAS's self-hosted IR gateway — enough to finish the 210M-row seed inside a single maintenance window without saturating the on-prem SQL Server that 40 other tables also depend on.
  • Built in the same Build wizard: Pipeline Settings exposes a Partition & chunking group for the Initial Load template — partition column, target chunk size (rows), and max parallel chunks — generated as the Lookup / ForEach / Copy shape above, not hand-authored.
  • One-time, then it's Incremental: once the chunked seed completes and reconciles, dbo.ClaimsIntake hands off permanently to the hourly Incremental/Delta pipeline already in the inventory table above — chunking only applies to the historical backfill, never to the steady-state hourly load.
!
Why not one big Copy activity with "parallel copies" just turned up?

Parallel copies alone (used for the steady-state hourly load) parallelizes within one activity run but the run still fails or succeeds atomically — a network blip at row 190M restarts the whole 210M-row extract. Chunking makes each ~10M-row slice its own restart unit, which is what actually matters for a one-time historical seed this large.

Target table & file naming standardization

The 43 objects land in only two kinds of destination — a curated lake table or a warehouse mart table — plus the archive/reject files the folder structure above already partitions by date. Each gets one fixed naming pattern, built from the same {source}/{object} tokens as the pipeline naming pattern, so a target name is never separately invented per object:

The target table (or target file) name is a field on each object's Onboarding row (§26.2), pre-filled from the pattern the moment the source object name is entered, and it round-trips into the generated dataset's physical name in Build's Target step — an author picks the connection, not a naming scheme. It's checked at the same warn/block enforcement points as pipeline names (Onboarding/Build inline, Validate, and the pre-push hard gate), so curated.PolicyMASTER or a table dropped straight in the schema root with no zone prefix is caught before a PR is even opened, not discovered by the next engineer who goes looking for it.

The _dq_status column above records the outcome; these are the checks that actually set it. Each is authored as a data quality rule on the object in Build's Pipeline Settings step — up to 5 per pipeline, each becoming a real pre-copy Lookup activity in the generated child pipeline, not a hand-written validation script:

This app never runs the check itself or inspects PAS's live data (§30.3's scope boundary) — the Lookup activity's SQL runs in ADF, at execution time, exactly like every other generated activity. Block is itself a Standards enforcement level (§25.2), so an org can make "primary key not-null, blocking" a required policy rule rather than a per-pipeline preference.

Trigger & cadence design

Daily — reference & low-churn tablesSchedule trigger, 02:00 UTC, after the legacy PAS nightly batch window closes. 9 reference tables + 28 long-tail objects.
Hourly — transactional tablesTumbling window trigger, 60-minute window with a 15-minute delay for late-arriving rows. ClaimsIntake, Endorsement.
Near-real-time — fraud event feedTumbling window trigger, 5-minute window, self-hosted IR polling a change-tracking table; storage-event trigger option evaluated but rejected — see note below.
!
Why "near-real-time" here means a 5-minute tumbling window, not literal streaming

ADF has no native sub-minute streaming primitive; a 5-minute tumbling-window trigger against SQL Server change tracking meets the actual business SLA (fraud scoring within 15 minutes of a claim event) without introducing a separate streaming platform (Event Hubs/Stream Analytics) that this migration doesn't otherwise need. Guide 2 covers a scenario where a real event-streaming source is already in play.

Orchestration design

Three separate orchestration shapes cover the 43 objects — chosen per the same rule as load type and cadence: don't force one pattern where it doesn't fit the object's actual dependency and concurrency needs.

Master/child — daily batch pl_pas_orchestrator_daily.json Lookup-reads the control table for objects due today, then ForEach (batchCount = 6) fans out an Execute Pipeline activity per object, wait-on-completion, with the object's parameters (table name, watermark column, load type). 37 child pipelines, one orchestrator.
Independent — hot hourly tables ClaimsIntake and Endorsement each run as their own tumbling-window pipeline, deliberately outside the master/child tree — one hot table stalling never blocks the other 41 objects, and vice versa.
Chunked — one-time historical seed The high-volume chunking shape above (Lookup → ForEach over the chunk-plan table → Copy per chunk → merge) runs once per table needing a large backfill, then is retired in favour of the object's normal load pattern.
Orchestratorpl_pas_orchestrator_dailyLookup control table → ForEach (batchCount 6)
→
Fan-outExecute Pipeline × 37One child per object, parameters passed, wait-on-completion = true
→
AggregateIf ConditionAny child status = Failed → orchestrator fails as one alert, not 37
→
DownstreamMart load pipelineTriggered only after the orchestrator succeeds — never on a fixed clock offset
  • Concurrency throttling protects the source, not just ADF: batchCount = 6 is set deliberately below what ADF could run in parallel — the ceiling is PAS's self-hosted IR gateway and the on-prem SQL Server's connection pool, not the platform.
  • No polling for "is curated ready yet": the Synapse mart-load pipeline is wired as a downstream dependency on the orchestrator's success (an Execute Pipeline call at the end of the master pipeline, not a separately scheduled trigger guessing at a safe time gap) — the mart never reads a half-updated curated zone.
  • Self-dependency on the hourly pipelines: the ClaimsIntake and Endorsement tumbling-window triggers use ADF's built-in tumbling-window dependency on their own previous window, so a run that goes long can never overlap with the next hour's run against the same watermark.
  • One failure surface: whether a failure comes from the daily orchestrator, an hourly independent pipeline, or a chunked backfill, all three write to the same execution log (Standard logging, above) — on-call has one dashboard, not three.

Built with ADF Forge — step by step

  1. Onboarding: Upload the 43-row object CSV (Upload → Map columns → Validate → Commit); 41 rows auto-map cleanly, 2 need a manual target-table correction flagged by validation.

  5.   6. Review & Generate: One click produces the full artifact set — pipeline, datasets, linked services, triggers, parameters — as a new DRAFT.
  7. Validate: ADF schema checks + the project's Standards policy run automatically; a naming violation on 2 objects is caught here, before any human review.
  8. Push to Git → PR: Selected, VALIDATED artifacts push to feature/pas-migration-batch-3; a PR opens into dev with the project's default reviewers prefilled.

Promoting onboarded source & control-table metadata

The ARM template in stage 2 only carries the ADF artifacts themselves — pipeline, dataset, linked service, trigger JSON. It says nothing about which of PAS's 43 tables are enabled, their watermark column, or their target path — that inventory lives in control.adf_control_table, the table the generated pipeline's Lookup activity reads at runtime to decide what to copy. Promoting that metadata is a parallel, environment-scoped step riding the same PR and the same CI/CD run as the ARM deploy above:

  1. Onboard or update the inventory in ADF Forge: Onboarding registers/edits PAS's 43 tables — target, format, load behavior, watermark column — via CSV import or the manual grid, then Generate control-table SQL produces <sql>/adf_control_table.sql (DDL plus one seed INSERT per enabled object) and an objects.csv snapshot — committed to the same feature branch and PR as the pipeline artifacts, never hand-typed against a live database.
  2. Reviewed alongside the pipeline diff (stage 1): a reviewer sees exactly which control-table rows changed — a newly enabled object, an edited watermark column — next to the pipeline JSON diff, so a metadata change gets the same scrutiny as a code change.
  3. Applied to Dev's control database (parallel to stage 3): a CI/CD step runs adf_control_table.sql against the Dev control-table database — connection resolved from Project Settings → Metadata & parameters, credential from Key Vault, never typed into ADF Forge or the script — with idempotent upserts so a re-run is always safe.
  4. Proven by the same smoke test (stage 4): the 9 reference-table smoke run succeeding confirms the ARM-deployed pipeline and the newly promoted control-table rows agree — it's the table's Enabled/WatermarkColumn values the Lookup activity actually reads at runtime.
  5. Promoted unchanged to Test, then Prod (stages 5–6): the identical adf_control_table.sql artifact — never hand-edited or regenerated per environment — is applied to Test's and Prod's own control databases under the same QA and change-advisory sign-offs as the ARM deploy, so "what passed Test is what runs in Prod" holds for the metadata driving the migration, not just the pipeline shape.
  6. Rollback: every adf_control_table.sql is retained and versioned by the CI/CD run number, exactly like the ARM template — a bad promotion (an object enabled too early, a wrong watermark seed) is fixed by re-applying the previous run's SQL artifact, never by hand-editing rows in a live control table.

Governance, cutover & rollback

  • Parallel run: New pipelines run alongside the legacy batch for 3 weeks; the execution log's rows_written per object is reconciled daily against the legacy job's row counts before any consumer is switched over.
  • Governance enforced throughout: naming pattern pl_pas_<object>_<load> at Block, required tags (data-domain, pii, source-system) at Block, Key-Vault-only secrets (always on), base-branch-must-be-dev (always on).
  • Rollback: redeploy the previous stage-2 ARM template artifact (every artifact is retained and versioned by the CI/CD run number) — never a manual edit against a live factory. A feature branch is reverted via a normal PR if the source of the regression is a bad artifact, not a bad deploy.
  • Decommission: once reconciliation holds for 2 consecutive weeks and both partner feeds confirm parity, the legacy SSIS job is disabled (not deleted) for a further 30-day cooling-off period, then retired.
